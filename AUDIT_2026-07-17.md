### 🟡 MITTEL — statistische Caveats & Konsistenz

**M1 — Kosten-Kennzahl im Walk-Forward ist optimistisch (in-sample Threshold) — ✅ DONE (2026-07-17)**
`training.walk_forward_eval` (`src/training.py:311-312`) bestimmt den kostenoptimalen Threshold `t_fold` **auf demselben Test-Fold**, auf dem danach die Kosten gemessen werden. Das ist ein In-Sample-Threshold → die berichteten „Kosten" sind eine **untere Schranke / optimistisch**, kein ehrlich erreichbarer Wert. Der Docstring gibt es zu („what would this model cost if operated well"), aber in der App/Report sollte das als Caveat stehen, sonst liest ein Revenue-Manager die Ersparnis zu optimistisch. **Sauberer:** Threshold auf Fold *k* aus den Folds *<k* bestimmen (oder nested), Kosten out-of-sample messen. Für die **Deployment**-Schwelle nutzt `retrain()` immerhin die gepoolten OOS-Predictions — das ist deutlich ehrlicher; nur die Fold-Kostenzahl ist der optimistische Teil.

**M2 — Hazard wird an zwei Stellen unterschiedlich gefittet (Ergebnis-Drift) — ✅ DONE (2026-07-17)**
`src/model_eval.py:206` fittet den Hazard pro Fold mit **eingefrorenen** HP (`fixed_hp=_hazard_hp()`), während `training.bakeoff_walk_forward` (`src/training.py:392`) und `hazard.walk_forward_eval_hazard` (`src/hazard.py:451`) pro Fold die **volle** RandomizedSearch (15 Iterationen) laufen lassen. Damit produzieren die **Model-Performance-Seite** und **Notebook 05 / die Hazard-Notebook-Evaluation** die „Hazard-Walk-Forward"-Zahlen mit **unterschiedlichen Verfahren** — nicht vergleichbar, und je nach Seite andere Zahlen. Kein Leak, aber inkonsistent. **Fix:** ein Verfahren festlegen (empfohlen: überall `fixed_hp=_hazard_hp()` für die Eval, Suche nur beim Retrain) und in allen drei Pfaden verwenden.

## 2. Was RICHTIG ist (bitte nicht „verschlimmbessern")

Damit du weißt, was du **nicht** anfassen solltest — das ist solide Arbeit:

- **Decision-time Walk-Forward** (`src/walkforward.py`): Jede Buchung wird genau einmal an ihrem Entscheidungsdatum `S* = max(created, arrival−H)` getestet; Train = Outcome vor Fensterbeginn bekannt; Point-in-Time per `assert_point_in_time` erzwungen. Löst korrekt das Short-Lead-Problem (nicht-überlappendes Arrival-Grid würde ~halbe Entscheidungs-Population verlieren).
- **Leakage-Governance:** `FEATURE_EXCLUSIONS` + `scoring_null_audit` (fängt Check-in-Felder, die auf Upcoming-Buchungen ~immer null sind). Roster ist die *einzige* Feature-Quelle für alle Modelle.
- **Family-aware Features:** LogReg = log-Twins + Scaling, Bäume = Rohspalten, ein Roster (`family_feature_lists`). Sauber getestet.
- **Kalibrierung:** `CalibratedClassifierCV` cross-fittet (kein Leak beim Refit auf Vollmenge). Zusätzlich **Decision-time-Rekalibrierung** gegen Survivorship-Bias (Basisrate ~20 % resolved vs. ~12 % zur Entscheidungszeit) — durchdacht.
- **Hazard-Modell:** diskrete Person-Period-Expansion, Per-Band-Isotonic (daily ≤14 vs. coarse tail), Survival-Produkt über die volle trainierte Snapshot-Grid, Pinning der Kategorien auf Train-dtype. Plus Poisson-Binomial-Varianz + Overdispersion-φ + Coverage-Report für die Aggregat-Ebene. Das ist echtes Senior-Niveau.
- **Kostenbasierter Threshold** statt F1 — für asymmetrische Walk/Empty-Kosten genau richtig; AP als Primärmetrik bei ~20 % Prävalenz + Brier-Gate für Kalibrierung.

## 3. FastAPI & „Online-Retraining" — ehrliche Einschätzung

Kurz und direkt, weil du mit FastAPI noch nicht gearbeitet hast:

### 3.1 Was FastAPI *ist* und was es hier *nicht* löst
FastAPI ist ein Web-Framework, um **HTTP-Endpunkte** zu bauen (z. B. `POST /score`). Es „retrained" **nichts** von selbst — das machst weiterhin du/dein Code. „Online-Retraining" wird oft mit FastAPI verwechselt; das sind zwei verschiedene Dinge:

- **Echtes Online-/Inkrementelles Lernen** (Modell pro neuem Sample updaten): XGBoost (dein Hauptmodell) ist **kein** Online-Learner. Deine Labels reifen zudem über **Tage bis Wochen** (eine Buchung „resolved" erst nahe Arrival), und die empfohlene Retrain-Kadenz im Code ist **~6 Monate** (`RETRAIN_INTERVAL_DAYS = 182`). Für so ein Problem ist inkrementelles Online-Lernen **statistisch nicht sinnvoll** — es bringt Instabilität ohne Nutzen.
- **Was du wirklich willst:** das Modell **periodisch als Batch neu fitten** auf allen bis „jetzt" resolveten Daten. Das hast du bereits: `main.py retrain`, `main.py update`, der App-Button (`run_retrain` → `tr.retrain`) und ein file-basierter Job-Runner (`dash_app/backend/jobs.py`, diskcache).

### 3.2 Brauchst du FastAPI? — Ehrliche Antwort: **jetzt nicht.**
Deine Architektur ist: Dash-App schreibt/liest Parquet, Scoring läuft im Batch, Retrain per Button/CLI. Es gibt **keinen externen Echtzeit-Konsumenten** im Repo, der pro Buchung einen HTTP-Score bräuchte. FastAPI würde jetzt vor allem **Betriebs-Oberfläche** (noch ein Prozess, noch ein Deploy, Auth, Modell-Loading) hinzufügen — **ohne echten Mehrwert**.

**FastAPI lohnt sich erst, wenn eines davon eintritt:**
1. Ein **anderes System** (PMS / Booking-Engine / Revenue-Tool) soll live pro Buchung eine Cancel-Wahrscheinlichkeit per API abrufen.
2. Du willst **Scoring vom Dash-Prozess entkoppeln** (eigener, unabhängig skalierbarer Score-Service).
3. Du willst Retrains per **Webhook** von außen triggern.

Wenn keiner der drei Punkte real ist → **kein FastAPI**. Der höherwertige, billigere Gewinn ist unten (3.4).

### 3.3 Falls doch (Punkt 1–3 trifft zu): schlanker, korrekter Weg
Halte es minimal und **trenne Scoring von Retraining strikt**:

- `POST /score` = **synchron**, read-only: lädt das joblib beim Start, ruft deine bestehende `score_reservations()`. Schnell, zustandslos.
- `POST /retrain` = **niemals synchron**. Retrain dauert Minuten (Hazard-Search!). Ein HTTP-Request darf nie darauf blockieren → **Job enqueuen** (dein `jobs.py`-Runner oder ein Scheduler) und sofort eine `job_id` zurückgeben; Status über `GET /jobs/{id}`.

Minimal-Skizze (nutzt **deine echten, verifizierten** Funktionen — FastAPI-Syntax bitte gegen aktuelle FastAPI-Docs prüfen, da ich API-Details nicht ungeprüft garantiere):
```python
# service/api.py  — SKIZZE, vor Einsatz gegen FastAPI-Docs verifizieren
from fastapi import FastAPI
import pandas as pd
from src.scoring import score_reservations, resolve_model

app = FastAPI(title="Overbooking scoring")

@app.get("/health")
def health():
    return {"ok": True, "model": resolve_model()}   # existierende Funktion

@app.post("/score")
def score(bookings: list[dict]):
    df = pd.DataFrame(bookings)                       # roh, PII-frei, wie load_reservations liefert
    out = score_reservations(df, apply_bounds=True)  # existierende Funktion
    cols = ["cancel_proba", "pred_cancel", "risk_bucket", "model_used"]
    return out[[c for c in cols if c in out.columns]].to_dict(orient="records")
```
Betrieb: `uvicorn` (oder `gunicorn -k uvicorn.workers.UvicornWorker`) — du hast gunicorn schon. Auth über euren bestehenden traefik-forward-auth. Retraining bleibt **Batch/Job**, nicht in der API.

### 3.4 Meine Empfehlung (harte, konkrete Reihenfolge)
Statt FastAPI zuerst die **echten** Lücken schließen — das bringt mehr, ist weniger Arbeit, und ist genau das, wonach ein Senior fragen würde:

1. **B1 fixen** (CLI-Crash) — 5 Minuten, sonst ist jeder geplante `score`-Lauf „rot".
2. **B2/B3 fixen** (Volume-Pfad + Roster-Regenerierung zur Laufzeit) — sonst ist jeder Deploy ein Glücksspiel.
3. **Scheduled Retrain** statt Online-Retrain: `main.py update` bzw. `main.py retrain --model hazard` per Cron/Scheduler (z. B. wöchentliches Rescoring, halbjährliches Retrain). Kein FastAPI nötig — das deckt „Modell aktuell halten" vollständig ab.
4. **`verify_pipeline.py` in CI** (M5) — deine Leakage-Garantie ist nur dann eine Garantie, wenn sie bei jedem Push läuft.
5. **Erst danach**, und nur bei realem externem Konsumenten (3.2, Punkt 1–3), einen dünnen FastAPI-`/score`-Service ergänzen.
